# Competitive benchmark results

Generated by `npm run eval:competitive` (1000 trials, seed 42). Same seeded fault schedule for every row; ground truth from the simulator's own store.

## Products and the behavior benchmarked

| product | pattern | documented behavior modeled | note |
|---|---|---|---|
| [Composio](https://docs.composio.dev/) | status trust | Tool execution returns the app's API response to the agent. Success = the API said ok. No read-back. |  |
| [Arcade.dev](https://docs.arcade.dev/) | status trust | Auth-first tool execution; the tool's return value is the API response. No read-back. |  |
| [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/tools/) | status trust | Function tools return the API response; a tool exception is fed back to the model as text (failure_error_function). Guardrails validate agent input/output, not tool side effects. | Model-driven re-tries are undefined behavior, so none are modeled. |
| [LangGraph RetryPolicy](https://reference.langchain.com/python/langgraph/types/RetryPolicy) | retry / replay | Node retried on ConnectionError, 5xx and transient errors; max_attempts=3 by default; checkpointer replays the node's writes. |  |
| [Temporal activity retry](https://docs.temporal.io/encyclopedia/retry-policies) | retry / replay | Activities retry on any failure with exponential backoff; maximumAttempts defaults to unlimited. At-least-once — idempotency is the user's job. | Unlimited attempts pinned to 3 so the benchmark terminates; more attempts only add more duplicates. |
| [tenacity](https://github.com/jd/tenacity) | retry / replay | @retry(stop=stop_after_attempt(3)) — retries on any exception. |  |
| [Guardrails AI](https://github.com/guardrails-ai/guardrails) | schema validation | Guard validates the output against a schema and validators; well-formed passes. Validators see the response, never the target system. |  |
| [Pydantic AI](https://ai.pydantic.dev/tools/) | schema validation | Tool return values are type-validated; ModelRetry (retries=1) re-asks the model on validation failure. Unhandled tool exceptions propagate. |  |
| [LLM-as-judge (Langfuse / Arize Phoenix evals)](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge) | response judge | A model scores the tool result for correctness. Modeled at its best case: a perfect reader of the response, zero latency. | A real model can only do worse on the same input, and adds latency and non-determinism. |
| [this repo (src/verifier.js + src/rollback.js)](https://github.com/gveshk/incident-responder-agent) | independent read-back | Write once. Re-read via a different path, tri-state verdict, rollback on false, escalate on unknown. Retry only a definitive 5xx (nothing was written); never a timeout. |  |

- **silent failures**: reality was wrong (no record, partial, unreachable, or duplicated) and the product told the agent "done"

## Caveats

- Trust-layer "orphaned writes" are all wrong-record cases: it correctly reports `false`, but the stray record lives under an id it was never given, so it cannot reverse it. A content search as a second source would close this; not implemented.
- Trust-layer escalations are timeouts plus read-path failures. Those go to a human instead of being guessed. That is the design, and it is a real cost.
- Retry rows are pinned to 3 attempts (LangGraph's default; Temporal's default is unlimited). More attempts only add duplicates.
- LLM-judge and mem0 are modeled at their best case (perfect decisions, zero latency). Real runs can only be worse on the same input.
- Vector-store top-k ties are broken by insertion order; any tie-break yields contradictory context whenever two owners are among the k most similar notes.
